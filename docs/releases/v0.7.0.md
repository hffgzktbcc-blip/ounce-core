# Ounce Core v0.7.0

Adds a local verification workbench and an instruction-level disagreement finder, fixes
several emulator and CLI behaviours, and widens the differential suite. The verification and
conformance claims are unchanged: nothing here claims independent reproduction, Neoverse
conformance or general libc compatibility.

## Added

- `ounce-core ui`: a local workbench on 127.0.0.1. Drop a homebrew `.nro`, run it on Tier-3
  and Tier-4, optionally compare with this computer's CPU, and see the first differing
  output line. It is one run, not a proof.
- `ounce-core diverge <program.nro>`: replays a sample of register-only instructions on this
  machine's CPU and names the first one where Ounce-Core disagrees (AArch64 hosts only; see
  `docs/DIVERGE.md` for limits). It traces the interpreter, Tier-3 and Tier-4 and reports a tier
  it could not run as NOT CHECKED. The workbench shows it as an "Instruction check" card.
- Static Linux ELF coverage: `run-elf` answers `sched_getaffinity`, so the pinned xxHash,
  cJSON and zlib harnesses run as static musl ELFs and match a host build on Tier-3 and
  Tier-4.
- QuickJS (46 scripts), QOI, tiny-AES-c, heatshrink, stb_image, LodePNG and a long-running soak
  workload join the differential suite; each matches a host build on Tier-3 and Tier-4.
- 18 real programs run as static Linux ELFs (BLAKE3 with NEON, Monocypher, Lua, QuickJS, SQLite,
  CoreMark, KISS FFT and others, pinned and fetched, not vendored) and match a host build,
  qemu-user, Tier-3 and Tier-4 where they were run; see `docs/verify/linux-elf/PROGRAMS.md` for
  what was and was not run on each host. wasm3 as an ELF still fails.
- A fixed 389,556-case floating-point edge corpus (`docs/verify/fp-edge`) runs on Linux Arm and
  Apple Silicon hardware and is replayed through all three engines: 0 mismatches at default FPCR.
  Floating-point rounding mode, flush-to-zero and default-NaN are now honoured by ordinary FP
  arithmetic (#363) through a pure-integer soft-float used only when those FPCR fields are set;
  the corpus gate now fails on a mismatch at any of the nine FPCR values, and it passed on Linux
  Arm and Apple Silicon hardware, replayed on the interpreter, Tier-3 and Tier-4 (Tier-4 hands off
  to the interpreter in those modes). Only the instructions in the corpus are covered: FP16
  arithmetic, FPSR exception flags and trap enables are not modelled.
- FMAXP/FMINP/FMAXNMP/FMINNMP, FMAXV/FMINV/FMAXNMV/FMINNMV and scalar pairwise forms are decoded
  and follow FPCR FZ/DN; Tier-4 takes the interpreter path for them. Half-precision min/max forms are also decoded: scalar, vector, pairwise and reduction
  forms honour FPCR.FZ16 and DN. These half-precision forms have pseudocode-based unit tests;
  hardware replay is not established. Scalar FADDP and scalar FMUL/FMLA/FMLS/FMULX by element are implemented; `run-elf`
  answers `mremap`.
- TestFloat vectors for `fuzz-replay`; every committed `.nro` replayed on the host CPU
  (22k instructions, 0 disagreements).
- Community guides, contributor onboarding, a citation file and a nightly fresh-seed fuzz.

## Fixed

- `LDPSW` sign-extends both loaded words (it was decoded as a 32-bit `LDP`), which made
  Monocypher's X25519 differ on every engine.
- Vector `FADD/FSUB/FMUL/FDIV` pick the NaN operand like Arm (signalling first, quieted);
  invalid operations return the positive default NaN on every host (x86 gave the negative one);
  scalar `FRINT*` and `FSQRT` quiet signalling NaNs. Found by the FP edge-case experiment.
- `FMAX`/`FMIN`/`FMAXNM`/`FMINNM` honour FPCR flush-to-zero and default-NaN. Before, 1,208 of
  4,800 replayed operand sets disagreed with the host CPU when either was set; now none do.
  Tier-4 no longer compiles scalar FMAX/FMIN natively.
- `run`/`run-nro --cpu=tier3|tier4` now selects that engine for homebrew programs. It was
  previously ignored, so earlier "Tier-3"/"Tier-4" NRO differential columns had run on the
  interpreter.
- The qc-flag harness masks FPSR[31:28] (RES0 without FEAT_AA32), resolving #257.
- CLI banners print the crate version instead of a hardcoded `v0.3.0`.
- Workbench on Windows and Linux (results folder, browser opener, closed stdout) and an
  `ounce-nce` arena test flake.

## The Mac app is not in the release assets

Per `docs/PROVENANCE_OWNER_DECISIONS.md` item 4 (objc2 and Apple SDK terms), no prebuilt
macOS app is attached to a GitHub release. It can be built from source with
`scripts/build_macos_app.sh`. It is a developer preview: ad-hoc signed, not notarized, and
its live-window acceptance (running a chosen program, failure-diagnosis card, host
verification, cancel/relaunch, Tier-4 in the GUI, Gatekeeper first open) is not claimed.

## Unchanged

CLI archives, notices, checksums and attestations are produced the same way as
[v0.6.1](https://github.com/hffgzktbcc-blip/ounce-core/releases/tag/v0.6.1) for Linux
x86-64, macOS arm64 and Windows x86-64. No new legal review or third-party grant is claimed.

## macOS launcher download

The release workflow also builds `ounce-core-macos-arm64-app.zip` for Apple Silicon, with a `.sha256` file and an entry in `SHA256SUMS`. The bundle includes licence notices. It is **unsigned by a Developer ID and unnotarized**, with only an ad-hoc signature. Unzip and move `Ounce Core.app` to Applications; on first launch, right-click > Open and confirm, or run `xattr -d com.apple.quarantine "/Applications/Ounce Core.app"` after verifying the source and checksum. Publication still requires the existing notice review; these changes do not publish a release.
