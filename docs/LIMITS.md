# What this does not prove

Each result in this project is evidence for a narrow statement. This page says, per claim, what the
evidence does **not** show. Numbers come from [docs/verify](verify/README.md) and [the vision](VISION.md); if a number here disagrees with the
per-harness README, the README wins. Terms: **"0 real mismatches"** is quoted from the CHANGELOG; no document in the repo defines "real" or lists any excluded case, and the classification is not saved in the repo; a **paper check** is a small program written for this repo from a paper or specification and compared with published test values ([papers](verify/papers/README.md)); **bounded-verified** is defined in [the maturity table](#maturity-labels-and-where-each-claim-sits).

| Claim | What it does NOT prove |
|---|---|
| Native execution output is byte-identical to the host reference | Native runs the guest on the host CPU and is available for NRO programs only (`run-elf --cpu=native` refuses and exits 72). On an ARM64 host it validates the harness, toolchain and loader only, **not the emulator**. Tier-3 and Tier-4 are the evidence for the emulator. On an x86 host native is unavailable. |
| Tier-3 and Tier-4 are byte-identical to the host reference on a harness | Agreement on the listed inputs only. It says nothing about inputs not in the harness, and nothing about instructions the harness never executes. Many vector, floating-point and system instructions are undecoded or untested. The engines share one decoder and Tier-3 and Tier-4 fall back to the interpreter, so their agreement with each other is a regression check, not independent evidence; the independent part is the reference. |
| QC-flag harnesses match the host (`qc-flag/saturating-shifts`: 5700 lines, 5684 with qc=1) | Most cases saturate (5684 of 5700), so the "QC clear" path and boundary cases just below saturation are barely exercised. A model that always set QC would pass almost all of them. The cumulative exception flags (IOC, DZC, OFC, UFC, IXC, IDC) are modelled in `FPSR` by the interpreter and Tier-3 (unit test `fpsr_exception_flags_accumulate_and_clear` in `src/cpu/interpreter.rs`), and Tier-4 hands FP to the interpreter once a program touches `FPSR`; trap enables are stored but never trap. The [qc-flag README](verify/qc-flag/README.md) predates this and still says the flags are not modelled. FPCR rounding mode, flush-to-zero and default-NaN are modelled for FP arithmetic, FMA, sqrt, FRINT*, single/double FCVT, int conversions and compares, and scalar half precision (#553, #554, #558), and match a qemu-user AArch64 reference on the fp-edge corpus at all nine FPCR values; real-hardware agreement was checked by the `fp-edge` CI job until `#548` (23 Nov 2026) removed that workflow; no CI job checks it today. The compiled Tier-4 form defers to the interpreter while any of those FPCR fields is set. |
| Results were compared against real ARM64 hardware | Only some were. The reference differs per suite: an Apple M3 (the single-instruction fuzzer, the 199-op FP workload, `#558`, the Big Tech native oracles), `qemu-aarch64` (the large TestFloat, Csmith, YARPGen, torture, MicroPython and PolyBench sweeps), a native x86-64 host build (the paper checks, PolyBench), or the suite's own expected values (s2n-bignum, secp256k1, libmpdec). The [evidence table](DETAILS.md#where-each-headline-number-comes-from) lists each one. Committed hardware references were recorded on Apple Silicon macOS arm64. The differential workflow also runs on Linux ARM64; [documented host differences](verify/README.md#hardware-differences) are retained rather than treated as agreement. This does not cover every ARM64 core or compiler. No outside machine has reproduced it yet ([REPRODUCE.md](REPRODUCE.md)). |
| Harness inputs are random plus edge values | Inputs are a finite fixed set (for example 300 or 400 operand sets per form). They are not exhaustive and not a proof of instruction-level correctness. The [single-instruction fuzzer](verify/insn-fuzzer/README.md) exists, with seeded biased inputs; it does not cover all instructions, FPCR modes or multi-instruction interactions. |
| Scalar FMAX/FMIN/FMAXNM/FMINNM NaN handling matches ([fmaxnm-nan](verify/fmaxnm-nan/README.md)) | Covers 15 single and 14 double edge values through the scalar forms, compared as output only. FMAX/FMIN already matched before the FMAXNM/FMINNM fix, but the scalar signalling-NaN ordering of FMAX/FMIN is not checked beyond those pairs, and the vector forms are a separate harness. Treat scalar SNaN ordering as unchecked outside the listed edge values. |
| LZ4, xxHash, SQLite, Lua, FP instruction test run correctly | The programs produced the same output as the host on the test cases in the harness. This is not a statement that the program or the emulator is correct everywhere. Additional merged harnesses are listed in [the manifest](verify/differential.json); each retains its own scope and evidence. |
| 50/50 outside programs pass the first-frame oracle | Each program matches a **registered pixel oracle** (whole-frame hash or named pixel probes, see [corpus-oracles.md](corpus-oracles.md)) on the interpreter and Tier-3. That shows the registered frame is reproduced, not that the program runs correctly, and not that any console or Switch compatibility holds. Native and Tier-4 are not part of this count. |
| Failure diagnosis and replay | One bounded workflow and one historical case (the SDL2 early exit). Diagnosis output is a hypothesis, not a root cause. |
| Hashes and evidence are retained | A matching hash shows the bytes match the declared digest, not independent provenance or a reproducible build. |
| Loader fuzz run found no panics | 300 inputs. A small run, not a security audit. |
| Speed | None claimed. One measured data point, on an Apple M3 under heavy load (load average 11 to 16, so a quiet machine is faster): the v0.12.0 release binary ran the `lucas-lehmer` [paper-check](verify/papers/README.md) program (470,102,283 guest instructions, built with the flags in [`docs/verify/papers/common/lib.sh`](verify/papers/common/lib.sh)) with `ounce-core run-elf lucas-lehmer.elf --cpu=<engine>`. The interpreter took 44.8 s and 47.6 s of CPU time in two runs (about 10 million instructions per second); Tier-3 took 26.9 s in one run (about 17 million per second). Tier-4 was not measured. |

## Known gaps in what the Linux ELF runner and CPU models execute (24 Nov 2026)

These are verified against the source at `main` (5247709, 25 Nov 2026, after #570) and the [Big Tech run](verify/bigtech-2026-11-23.md):

- **`AT_HWCAP` is `0x2201fb`** (FP, ASIMD, AES, PMULL, SHA1, SHA2, CRC32, ATOMICS, SHA3, SHA512). `FEAT_AES`, `FEAT_SHA1`, `FEAT_SHA2` and `FEAT_SHA512` execute on every engine and match an Apple M3 bit for bit on the inputs listed in the [changelog](../CHANGELOG.md); `FEAT_SM3` and `FEAT_SM4` are not implemented.
- **Linux system-register ABI:** `HWCAP_CPUID` is deliberately not advertised, so `MIDR_EL1`, `MPIDR_EL1`, `REVIDR_EL1` and the `ID_AA64*` registers fault instead of returning invented values. This follows [ARM64 CPU Feature Registers, sections 1–4](https://docs.kernel.org/arch/arm64/cpu-feature-registers.html), where the kernel advertises ID-register emulation with `HWCAP_CPUID`, and [ARM64 ELF hwcaps, section 3](https://docs.kernel.org/arch/arm64/elf_hwcaps.html#the-hwcaps-exposed-in-at-hwcap). `CTR_EL0` reports 64-byte instruction and data cache lines. Linux `CNTFRQ_EL0` is 1 GHz and `CNTVCT_EL0` uses host monotonic nanoseconds normally or the retired-instruction counter under `--deterministic`; inaccessible or unknown system registers raise guest `SIGILL` (see the next item).
- **Guest faults become Linux signals:** UDF and the rest of the reserved encoding class, `MSR` to an EL1 register, and any other EL0 system-register access Linux does not expose raise `SIGILL` (`ILL_ILLOPC`, `si_addr` = the PC); a misaligned `LDXR`/`LDAXR`/`STXR`/`STLXR`/`LDXP`/`LDAXP`/`STXP`/`STLXP` raises `SIGBUS` (`BUS_ADRALN`, `si_addr` = the address), and a faulting `STXR` neither stores nor writes its status register. These follow `arch/arm64/kernel/traps.c` and `arch/arm64/mm/fault.c`; a guest handler runs on the same frame as `SIGSEGV` and with no handler, or with the signal ignored or blocked, the run ends with status 132 (`SIGILL`) or 135 (`SIGBUS`) and a diagnosis. Valid encodings ounce-core has not implemented stay a stop with the unimplemented-instruction diagnosis (`ounce.run.v1` exit 10), because that is an emulator gap, not a guest fault. Ounce-core does not advertise `HWCAP_USCAT` (FEAT_LSE2), so exclusives must be aligned to their size; the Apple M3 and other LSE2 cores fault only when the access crosses a 16-byte boundary ([evidence](verify/sigill-sigbus/README.md)). Not done: misaligned LSE atomics (`CAS`, `LDADD`, ...) and `LDAR`/`STLR` do not fault, `LDXP Rt, Rt` still stops as unimplemented, and only the reserved class is UNDEFINED, so other unallocated words that the decoder does not know still report as unimplemented. Horizon guests (`run-nro`) keep the unimplemented-instruction stop for UDF.
- **Exclusive monitor:** one local monitor per CPU that tags the address and size of the last load-exclusive. `STXR` succeeds only for the same address and size; `CLREX`, any store-exclusive and a thread switch clear it. Differing size or address is CONSTRAINED UNPREDICTABLE in the architecture (the Apple M3 lets the store succeed; ounce-core fails it, the conservative result for a retry loop). An *ordinary* store between `LDXR` and `STXR` does not clear the monitor: whether it does is IMPLEMENTATION DEFINED and the M3 clears it for the same 16-byte granule, but Tier-4 stores run natively and cannot be observed, so no engine clears it, and not clearing cannot turn a correct retry loop into a livelock. Code that depends on such a store clearing the monitor is not portable.
- **Linux clocks:** `--deterministic` starts `CLOCK_REALTIME` at `1700000000.000000000` and the monotonic-family clocks at `0.001000000` on their first successful read; each later successful wall/monotonic read advances 1 ms. `CLOCK_PROCESS_CPUTIME_ID` and `CLOCK_THREAD_CPUTIME_ID` are available as Linux specifies in [`clock_gettime(2)`](https://man7.org/linux/man-pages/man2/clock_gettime.2.html); this single-threaded runner reports retired-instruction-derived CPU time in deterministic mode, at one nanosecond per instruction.
- **`futex` is not implemented**, and there are no guest threads (`clone` with thread flags returns `ENOSYS` with a one-time stderr note): run single-threaded guests only. Plain `cargo test` works without `--test-threads=1` because libtest catches the `ENOSYS`/`WouldBlock` failure on thread creation and executes tests sequentially inline on the main thread, while programs that spawn second threads (e.g. `std::thread::spawn`) fail with `WouldBlock` / `EAGAIN`.
- **Files are a bounded in-memory scratch area**: `/tmp` and `/var/tmp` (at most 64 files and 64 open descriptors, 16 MiB per file, 64 MiB in total), plus `/dev/null` and `/proc/self/auxv`. Other paths fail with `ENOENT`. Nothing reaches the host file system. Guest `getrandom` is a fixed stream, so a program that needs real entropy sees the same bytes every run.
- **Standard input is empty** unless you pass `--stdin` or `--stdin=<path>` (64 MiB limit).
- **Static, non-PIE only.** `ET_DYN` and static-PIE are rejected.

Not established at all: running arbitrary ARM64 or Linux applications, and automatic root-cause finding.

## Maturity labels and where each claim sits

| Label | Meaning |
|---|---|
| research-only | explored, not dependable |
| bounded-verified | matches a named reference (hardware, `qemu-aarch64`, a native host build or the suite's own expected values) on the listed inputs, with retained evidence; says nothing about other inputs, and the engines share a decoder, so engine-vs-engine agreement alone does not qualify |
| independently reproduced | someone outside the project reran it and got the same result |
| publicly supported | documented, versioned, and maintained for users |

| Claim | Label today |
|---|---|
| Tier-3 / Tier-4 / native match the host on LZ4, xxHash, SQLite, Lua | bounded-verified |
| Differential harnesses for floating-point, vector, QC and saturating instructions (hardware reference) | bounded-verified on the listed inputs |
| Additional library harnesses | see individual harness results; merging alone establishes no correctness claim |
| Instruction-level checking against hardware in general | research-only |
| 50/50 first-frame oracle corpus | bounded-verified for the registered pixel oracles only |
| Diagnosis and replay of a historical failure | bounded-verified (one workflow, one case) |
| Anything reproduced by an outside party | none yet; this is what [REPRODUCE.md](REPRODUCE.md) and the tracking issue ask for |
| Versioned diagnosis toolkit | released 0.2.0 for the [documented CLI scope](DIAGNOSIS_CLI.md); no general runtime support claim |

No outside reproduction is recorded here. The standalone diagnosis toolkit release does not establish public support for arbitrary runtime inputs.
