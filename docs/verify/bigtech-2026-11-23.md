# Big Tech and fintech library runs, 23 Nov 2026

Seven open-source libraries that real products depend on, built as static AArch64 Linux ELFs and run
with `ounce-core run-elf` on the interpreter, Tier-3 and Tier-4 engines. This page records what ran, what
passed and what did **not** finish. Run on an Apple M3 Mac, 23 Nov 2026 (run by Claude agents under Orca on the
maintainer's machine, not an independent reproduction). The raw logs and the upstream sources are not committed; the upstream
commits below let you rebuild them.

`ounce-core` (per the run notes): stock `main` at `0bce1d3` for every row except simdjson `-O3` and SGP4 `-O3`, which were re-run after
#559 (FEAT_LSE atomics; `main` at `14b3c4d`). Before #559 those two `-O3` builds (`-mcpu=apple_m1`, which emits LSE instructions) were blocked because the engines ran those atomics as plain loads and stores.

Caveats that belong with the numbers:

- **s2n-bignum: 13 skipped, not passed.** The skipped tests need `FEAT_AES`, which `ounce-core` does not implement. The suite prints "Skipping ... (ARM aes/sha3 support)". The native M3 run executes all 397.
- **secp256k1: Tier-3 and interpreter did not finish.** They were stopped or killed for time with no failure printed. Only Tier-4 completed all 119 tests. Do not read this row as three-engine agreement.
- **libwebp `-O3` on the interpreter was not run.**
- **SGP4: 260 of 1,222 lines differ from the oracle.** The differing lines differ by 1 to 2 ulp (median), which is consistent with the macOS libm used by the oracle versus the musl libm used in the guest. That attribution is **not verified**: the differences are unclassified, and no libm-independent oracle exists yet. The three engines agree byte for byte with each other.

## What each run compared

For BLAKE3, libwebp, simdjson and SGP4 a driver program prints deterministic text. The same driver built
natively with `clang -O2` on the M3 produced the oracle file. `run-elf` output is compared with that file.
libmpdec reads each `decTest` file through `--stdin=<file>`; simdjson reads each JSON file the same way.

## Commands

Build (from the scripts used; `<suite>` flags are in the table above). Zig's `cc` front end (clang) built the
guest ELFs (Zig 0.17.1, the official ziglang.org macOS aarch64 tarball unpacked to `/tmp/zig`; the run record says it was sha256-verified, and the scripts call `/tmp/zig/zig`).

```sh
# -O2 guest build, then -O3 build for an Apple M1-class target
zig cc -target aarch64-linux-musl -static -no-pie -O2 <suite flags and sources> -o suite_O2
zig cc -target aarch64-linux-musl -static -no-pie -O3 -mcpu=apple_m1 <suite flags and sources> -o suite_O3
# C++ suites (simdjson -std=c++20, SGP4 -std=c++17) use `zig c++`
# s2n-bignum -O2 used: -mcpu=generic+sha3+aes+crypto; its assembly is built with -c, then linked with tests/test.c
# native oracle build: clang -O2 <same sources> -o suite_native   (Apple M3)
```

Run each engine (the `--max-insns` value is the larger budget the runs needed):

```sh
for cpu in interpreter tier3 tier4; do
  ounce-core run-elf suite_O2 --cpu=$cpu --max-insns=400000000000 [--stdin=<file>] [-- <suite args>] > out.$cpu
done
```

Suite arguments: s2n-bignum `-- +5`; secp256k1 `-- -log=1 -iterations=1 -seed=0123456789abcdef0123456789abcdef`;
libmpdec `--stdin=<name>.decTest -- -`.

## What this does not show

Counts are for these builds, inputs and compiler flags only. They are not a statement that the libraries
or the emulator are correct in general, and a passing run is not an outside reproduction. See
[LIMITS.md](../LIMITS.md) for known gaps (`FEAT_AES`, `LDXP`/`STXP`, `futex`, `HWCAP_ATOMICS`).
